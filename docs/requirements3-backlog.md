# 3차 요구사항 백로그

[3차 요구사항 분석](requirements3-analysis.md)을 작업 카드로 나눈 초안. 2차와 같은 방식(기능 단위 카드, 각자 가져가기, 카드 하나에 GitHub Issue 하나)으로 진행한다. 카드를 가져가거나 끝낼 때마다 이 표를 갱신한다.

- 카드 번호는 2차(0~13)에 이어서 14번부터 쓴다.
- 날짜 형식: `YYYY-MM-DD`
- 상태: ⬜ 대기 / 🔄 진행 중 / ✅ 완료
- 완료 기준: 테스트 추가, **상대방 GitHub Review 후** 이슈를 닫는 PR(`Closes #번호`) 머지, 필요한 문서 갱신
- 진행 중인 카드는 한 사람당 1장

## 카드별 내용

### 14. 3차 안건 확정과 이슈 등록

- [분석](requirements3-analysis.md) 5장의 안건 ⑩~㉔를 팀 논의로 정하고 [미확정 사항](open-questions.md)에 결정과 근거를 기록
- 분석 7장에 따라 N3-01의 입력 시작점·화면 표시 완료점, 조작 종류, 반복 횟수, 측정 방법·오차를 정하고 측정 절차로 기록
- 카드 15~28을 GitHub Issue로 등록하고 GitHub Projects 보드에 올림
- 완료 기준: 안건 결정 기록, N3-01 측정 절차 확정, 이슈 등록

### 15. core 리팩터링: 대기 줄 반영 지점

- 블록 고정 → 아이템 효과·줄 삭제 → 대기 공격 반영 → 넘침 판정 → 다음 블록 생성. 아이템 세부 규칙은 안건 ⑭·⑮로 확정하되, 다음 블록 생성 전 공격 반영(R3-08)을 유지
- 공급자처럼 외부 줄을 받는 인터페이스를 두고, 넘침이면 다음 블록을 생성하지 않고 논리적 패배를 보고
- `Board`에 아래에서 줄 밀어 넣기. 위로 밀려 보드 밖으로 나가는 칸이 있으면 종료 (안건 ⑩)
- 공격 칸 전용 모양(`TemporaryBlock`과 같은 방식)
- 기존 1인 게임 동작은 바뀌지 않음 (기존 테스트 전부 통과)
- 완료 기준: 줄 추가·넘침·생성 실패, 아이템 효과·줄 삭제와 공격 반영 순서 테스트. 패배를 결과 연출과 독립적으로 관찰할 수 있는지 확인하고 기존 자동 플레이 검증 재실행

### 16. 공격 줄 계산과 대기열

- R3-06에 따라 `EngineStep`의 지운 줄 칸 내용(`ClearedRow`)에서 마지막 블록 칸(`LockResult`)을 뺀 모양 계산. 아이템에 의한 공격 여부는 안건 ⑭, 무게추의 공격 모양은 안건 ⑮ 적용
- 공격 줄의 기존 칸에 남아 있는 아이템의 전달 여부는 안건 ㉔의 결정 적용
- 2줄 이상일 때만 공격
- 대기열: 최대 10줄, 새 공격은 아래에 추가, 이미 10줄이면 무시, 넘치면 제일 아래 잘라냄
- 완료 기준: p4 예제(L자 블록으로 3줄 삭제), 1줄 삭제 시 미공격, p6 규칙 4가지와 행 순서 보존 테스트. 기존 8줄 + 새 3줄은 기존 8줄과 새 공격의 위쪽 2줄만 보존하며, 합계 정확히 10줄·이미 10줄인 경우도 검증

### 17. 로컬 대전 세션

- 세션 두 개를 묶어 공격 전달, 한쪽 종료 시 상대 승리, 동시 종료 처리(안건 ⑬)
- 일시정지는 둘 다 정지(안건 ⑱), 종료 후 흐름은 일반 게임과 같되 스코어보드 기록 안 함
- 두 플레이어 블록 순서(안건 ⑰), 난이도 적용(안건 ⑯)
- 논리적 패배 확정과 삭제·결과 연출을 분리하고, 확정 뒤 양쪽 게임 진행을 중단. 동시 판정과 시간 만료 경합은 안건 ⑬·㉓ 적용
- 완료 기준: 공격 → 대기열 → 다음 블록 전 추가 순서, 승패, 미기록, 일시정지·재개·나가기 테스트. 삭제 연출 중 공격 도착·패배와 확정 이후 추가 점수·공격이 발생하지 않음을 검증

### 18. 2P 키 설정

- 설정 화면에 2P 조작 키, 1P·2P 사이 키 충돌 거부, 기본 키(안건 ⑲)
- 기존 설정을 보존하며 2P 설정을 추가. v2 → v3 변환은 구현 제안이며 채택한 호환 방식 기록
- 기존 사용자 키와 새 2P 기본값이 충돌할 때 처리 정책 결정. 기존 키를 임의로 덮어쓰지 않고 대체 2P 기본값 또는 명시적 재설정 안내 제공
- 완료 기준: 기존 설정 불러오기·저장·재실행, 기존 키와 2P 기본값 충돌, 공통 키 처리, 기본값 복원 테스트

### 19. 대전 화면과 메뉴

- 시작 메뉴에 "대전 모드", 모드 선택 화면(일반 / 아이템 / 시간제한)
- 보드 2개, 각자의 NEXT·점수·대기 줄 영역, 승자 표시. 공격 칸은 회색 + 전용 무늬(색맹 모드 포함)
- 플레이어별 입력 매퍼와 반복 입력 (동시에 눌러도 서로 무시되지 않음)
- 넓은 격자를 쓰는 화면에 맞춰 창 크기 조정, 화면 크기 3단계 유지
- 완료 기준: 화면 로직 테스트(창 없이), 두 명 동시 입력 테스트

### 20. 시간제한 모드

- 시간(안건 ⑪), 남은 시간 표시, 시간 종료 시 점수 비교, 동점(안건 ⑫)
- 일시정지 중 제한시간 처리, 시간 만료와 패배·공격의 우선순위, 만료 후 입력 차단을 안건 ⑱·㉓에 맞춰 구현
- 완료 기준: 가짜 시계로 만료 직전·정확한 경계·직후의 입력과 점수, 동점, 일시정지·재개, 삭제 연출 중 시간 만료 및 패배와의 경합 테스트

### 21. 대전 아이템 모드

- 플레이어마다 아이템 공급자, 아이템으로 지운 줄과 공격의 관계(안건 ⑭)
- 아이템으로 지운 줄의 공격 모양·기존 빈칸 보존은 안건 ⑭·⑮, 공격 줄에 남은 아이템의 전달 여부는 별도 안건 ㉔로 확정. 양쪽 블록 순서는 안건 ⑰의 범위 적용
- 완료 기준: 아이템별 공격 여부·행 모양·빈칸·전달 속성 테스트. 두 플레이어의 아이템 효과가 독립적임을 검증. P2P에서 같은 규칙을 사용하는지는 카드 24의 통합 완료 기준으로 검증

### 22. 통신 포트와 소켓 어댑터

- application에 통신 포트(연결, 송수신, 연결 상태), `network` 패키지에 소켓 구현
- 메시지 형식은 명시적 형식으로 정의. 접속 직후 버전을 교환하고 안건 ⑳의 동일 빌드 / 호환 프로토콜 정책 적용
- 로비·준비·시작·상태 또는 입력·공격·정지·재개·결과·나가기·ping 메시지의 필드와 허용 상태를 정의. 경기 식별자, 필요한 순서 정보와 중복 이벤트 처리 계약 포함
- 수신 결과를 게임 실행 흐름에 전달하는 경로와 UI 반영 경로 정의. 수신 스레드가 세션을 직접 변경하지 않도록 함
- 확인 메시지(ping)로 RTT 측정. 입력→화면 200ms 검증과 별개임을 기록
- 완료 기준: 메시지·호환성·실행 흐름 계약, localhost 접속·송수신·비호환 연결 거부, 잘못된 상태·이전 경기 메시지 처리와 중복 공격 방지 테스트

### 23. P2P 로비

- P2P 첫 화면에서 서버/클라이언트 선택
- 서버: 사용 가능한 IP 표시 후 대기. 클라이언트: IP 입력, 최근 IP 목록에서 선택
- 연결 완료 표시, 서버가 모드 선택, 양쪽 모두 '게임 시작'을 눌러야 시작
- 최근 IP 저장(`storage`, 기존 원자적 저장 방식), 파일이 없거나 깨져도 실행
- 접속 단계별 메시지(대기 중, 접속 중, 연결됨, 실패 사유)
- 완료 기준: 로비 상태 전이·최근 IP 저장소 테스트. 한쪽만 준비했을 때 시작되지 않음, 서버의 모드·시간 변경 시 준비 처리, 양쪽 준비 후 한 번만 시작, 재대전 준비 초기화를 검증

### 24. P2P 대전 진행

- 시작 조건: 17·23 완료 후 개발 가능. 완료 조건: 19·20·21의 화면·시간제한·아이템 기능과 통합
- 동기화 방식과 상태 관리 계약(안건 ⑳)에 따라 양쪽 화면, 공격 전달, 일시정지·재개·나가기, 결과 확정 구현
- 시간제한은 합의한 기준 시계와 종료 우선순위 적용. 서버 기준 시계는 분석 문서의 제안이며 카드 14에서 확정
- 끝나면 양쪽에 같은 승패를 표시하고 연결을 유지해 로비로 복귀. 재대전 시 보드·점수·공격 대기열·타이머·아이템 효과·준비 상태 초기화
- 완료 기준: 일반·아이템·시간제한 각각에서 양쪽 화면, 공격, 승패 일치, 점수 미기록을 자동화 검증. 각 모드에서 결과 표시 → 로비 복귀 → 양쪽 준비 → 두 번째 경기까지 확인하고 이전 경기 메시지가 새 경기에 적용되지 않음을 검증
- 성능 완료 기준: 분석 7장의 N3-01 절차에 따라 실제 같은 LAN의 PC 두 대에서 양방향 입력→로컬·상대 화면 지연을 측정하고 최대값·200ms 초과 횟수·측정 오차 기록. localhost 결과나 ping RTT만으로 완료 판정하지 않음

### 25. 네트워크 문제 처리

- 시작 조건: 카드 24의 기본 송수신이 동작하면 병행 가능
- 랙·끊김 기준(안건 ㉑), 측정 주기와 회복 기준을 문서에 기록
- 랙이면 화면에 표시하고 회복하면 해제. 끊기면 에러 메시지 후 P2P 첫 화면으로 복귀하며 소켓·수신 작업 정리
- 완료 기준: 가짜 통신으로 지연·회복·끊김을 만들어 표시·해제·화면 전환 검증. 실제 소켓의 종료·자원 정리 후 재접속이 가능함을 localhost 테스트로 확인

### 26. 네트워크 자동화 테스트

- 22~25를 진행하며 함께 작성. 접속 성공, 잘못된 IP, 비호환 버전, 접속·로비·게임 중 끊김, 랙 회복과 재접속 검증
- 세 모드 진행·연속 두 경기·이전 경기 메시지 차단·일시정지 동기화·종료 경합을 카드 23~25의 테스트와 연결. 각 카드의 테스트를 재사용하고 중복 작성하지 않음
- CI(GitHub Actions)는 localhost 소켓과 가짜 통신·가짜 시계를 사용. 실제 LAN 성능 실측은 카드 24, 배포 리허설은 카드 28에서 수행
- 완료 기준: 관련 자동화 테스트가 CI에서 통과하고 요구사항별 테스트 위치를 기록. CI 결과로 실제 LAN의 N3-01 충족을 대신하지 않음

### 27. 팀 아이템 요구사항 명세서 재작성

- 수업의 요구사항 명세 형식으로 `C`·`B`·`$` 재작성: ID, 설명, 형태, 발동 조건, 효과, 점수, 우선순위, 수용 기준, 관련 테스트
- 초안은 독립 작성 가능. 대전 아이템 모드 규칙(카드 21)의 공격 여부·모양·전달 속성 정책도 포함
- 완료 기준: 카드 21의 결정·구현·테스트와 명세가 일치하고 상대방 리뷰 완료

### 28. v3.0.0 릴리즈

- 1·2·3차 요구사항 전수 재점검, [요구사항 추적표](requirements-traceability.md)에 3차 항목 추가
- 커버리지 70% 이상 유지 확인 및 보고서 보관, 버전 3.0.0, `packageZip`, GitHub Release
- 배포 빌드로 시연 노트북 두 대의 방화벽·P2P 세 모드·재대전 리허설. 분석 7장의 실제 LAN 성능 측정을 재확인하고 예비 네트워크 준비
- 저하 환경의 랙 표시·회복·끊김·재접속 결과는 정상 LAN 성능과 구분해 기록
- 완료 기준: Release, 요구사항별 자동화 테스트·실측·리뷰 증거를 연결한 추적표, 커버리지 보고서와 리허설 기록. N3-01 초과 또는 측정 불확실성은 개선·재검증 후 완료 판정

## 진행 순서 제안

```
14 ──┬─ 15 ── 16 ── 17 ──┬─ 19 ──┬─ 20
     │                   │       └─ 21
     ├─ 18 ──────────────┘
     └─ 22 ── 23 ── 24 (시작: 17도 필요 / 완료: 19·20·21 통합 + LAN 실측)
                     └─ 25 (24 기본 송수신부터 병행)
27은 독립 착수, 완료 시 21과 일치 확인
26은 22~25와 함께, 28은 마지막
```

- 두 줄기로 나눠 동시에 진행할 수 있다: **대전 규칙 줄기**(15 → 16 → 17 → 19 → 20·21)와 **네트워크 줄기**(22 → 23 → 24, 기본 송수신 이후 25 병행).
- 18(2P 키)은 14 이후, 27(명세서) 초안은 독립적으로 진행한다. 27 완료에는 21의 규칙·구현과 일치 확인이 필요하다.
- 24는 17·23 이후 시작하되, 19·20·21과의 통합·세 모드 재대전·실제 LAN 성능 검증까지 마쳐야 완료한다. 25는 24의 최종 완료를 기다리지 않고 기본 송수신부터 병행한다.

## 도전 과제 (선택)

요구사항 p12에 따라 **별도 브랜치에서 개발하고 main에 머지하지 않는다.** 점수는 없지만 시연 득표에 유리하다.

| 과제        | 브랜치 예시                 | 메모                                            |

| 컴퓨터 대전 | `challenge/computer-player` | 2차 검증에 쓴 자동 플레이 방식을 응용할 수 있음 |
| P2P 채팅    | `challenge/p2p-chat`        | 카드 22의 메시지 형식에 채팅 메시지 추가        |

## 갱신 방법

1. 카드를 가져갈 때: 이슈 담당자를 지정하고 보드에서 "진행 중"으로 옮긴다. 이 표의 상태를 🔄로 바꾸고 담당과 시작일을 적는다.
2. PR이 머지되면: PR 본문의 `Closes #번호`로 이슈가 닫혔는지 확인한다. 이 표의 상태를 ✅로 바꾸고 완료일과 PR 번호를 적는다. 요약 표의 카드 수도 고친다.
3. 안건이 결정되면 [미확정 사항](open-questions.md)에 기록하고, 관련 카드의 내용을 결정에 맞게 고친다.
