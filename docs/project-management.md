# 프로젝트 관리 규칙

할 일 배정, 진척 관리, 브랜치·PR, 이슈 추적을 어떻게 하는지 정리한 문서입니다. 1·2차 요구사항의 프로젝트 관리 항목(Trello 등으로 진척·배정 관리, Git·GitHub 버전 관리와 브랜치·PR 정책, 이슈 등록과 해결 추적)에 대응합니다.

## 1. 기록 위치

| 무엇을 | 어디에 |
| --- | --- |
| 할 일(카드)과 담당자, 진행 상태 | Trello 보드 (백로그 / 진행 중 / 완료) |
| 카드별 담당·시작일·완료일·PR | [백로그 진행 현황](requirements2-backlog.md) |
| 문제와 해결 과정 | GitHub Issues |
| 코드 변경과 리뷰 | GitHub Pull Requests |
| 빌드·테스트·커버리지 결과 | GitHub Actions (`.github/workflows/ci.yml`) |
| 설계 결정과 요구사항 해석 | [아키텍처 결정 기록](architecture-decision.md), [미확정 사항](open-questions.md), [요구사항 추적표](requirements-traceability.md) |
| 배포 파일 | GitHub Releases (`v<버전>` 태그) |

## 2. 작업 흐름

1. **카드 가져가기**: 백로그 위쪽에서 선행 카드가 끝난 카드를 가져갑니다. Trello 카드를 "진행 중"으로 옮기고 담당자를 지정합니다. [백로그 진행 현황](requirements2-backlog.md)에 상태 🔄, 담당, 시작일을 적습니다.
2. **이슈 만들기**: 카드마다 GitHub Issue를 하나 엽니다. 제목은 카드 이름, 본문에는 할 일과 완료 기준을 적고 라벨과 담당자를 지정합니다. Trello 카드에 이슈 링크를 붙입니다.
3. **브랜치 만들기**: 최신 `main`에서 아래 규칙에 맞는 브랜치를 만듭니다.
4. **작업과 커밋**: 테스트를 함께 추가하고, 커밋 메시지는 아래 규칙을 따릅니다.
5. **PR 올리기**: `main`으로 PR을 올리고 본문에 `Closes #이슈번호`를 적습니다. CI가 통과해야 합니다.
6. **리뷰와 머지**: 상대방이 리뷰하고 승인한 뒤 머지합니다. 자기 PR을 리뷰 없이 머지하지 않습니다.
7. **마무리**: 이슈가 자동으로 닫혔는지 확인합니다. Trello 카드를 "완료"로 옮기고 백로그에 상태 ✅, 완료일, PR 번호를 적습니다. 머지된 브랜치는 삭제합니다.

진행 중인 카드는 한 사람당 1장을 원칙으로 합니다. 같은 PR로 묶어야 하는 카드는 백로그 비고에 함께 적습니다.

## 3. 브랜치

| 접두어 | 용도 | 예 |
| --- | --- | --- |
| `feat/` | 새 기능 | `feat/team-items` |
| `fix/` | 버그 수정 | `fix/visible-spawn` |
| `refactor/` | 동작을 바꾸지 않는 구조 변경 | `refactor/core-model` |
| `docs/` | 문서만 변경 | `docs/backlog-update` |

- `main`은 항상 빌드와 테스트가 통과하는 상태로 유지합니다. `main`에 직접 커밋하지 않고 PR로만 합칩니다.
- 앞 PR이 머지되기 전에 이어서 작업해야 하면 앞 브랜치에서 새 브랜치를 만들고, PR의 base도 앞 브랜치로 지정합니다. 앞 PR이 머지되면 base를 `main`으로 바꿉니다.

## 4. 커밋 메시지

```
<타입>(<범위>): <요약>

- 변경 내용 1
- 변경 내용 2
```

- 타입: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`
- 범위(선택): `core`, `ui`, `item`, `pieces` 등 바뀐 영역
- 요약은 한국어로, 무엇을 바꿨는지 한 줄로 적습니다.

## 5. Pull Request

- **제목**: 커밋 메시지 규칙과 같은 형식
- **본문**: 변경 요약, 테스트·검증 방법, 관련 이슈(`Closes #번호`)
- **머지 조건**: CI 통과, 상대방 리뷰 승인, 관련 문서(백로그, 추적표, 명세서) 갱신
- **머지 방식**: 커밋 기록을 남길 가치가 있으면 Merge commit, 여러 작업 커밋을 하나로 묶을 때는 Squash merge

## 6. 이슈

- 카드 하나에 이슈 하나를 엽니다. 작업 중 발견한 버그나 요구사항 해석 문제도 따로 이슈로 엽니다.
- 라벨: `feature`, `bug`, `refactor`, `docs`
- 해결 내역은 이슈 댓글과 연결된 PR로 남깁니다. e-class에 문의한 질문은 이슈에 질문과 답변을 기록합니다.

## 7. 릴리즈

1. `build.gradle`의 `version`을 올립니다. (1차 `1.0.0`, 2차 `2.0.0`)
2. `.\gradlew.bat clean build packageZip`으로 테스트와 배포 zip을 만듭니다.
3. 압축을 푼 `SETetris.exe`를 더블클릭해 실행을 확인합니다.
4. GitHub Releases에 `v<버전>` 태그로 zip을 올립니다.
