# 아키텍처 결정 기록 (ADR)

## 결정: 헥사고날(포트-어댑터) 아키텍처 채택

### 배경
팀원 세 명이 각각 MVC, 헥사고날, 패키지-바이-레이어 구조를 제안. 강의 취지("실무에서 어떤 요구사항이 올지 모르므로 대응 가능한 구조를 짤 것")를 기준으로 비교 검토함.

### 결정 근거
- 예측이 아니라 격리: 특정 변화를 예측해서 대비하는 대신, core(도메인 규칙)와 그 바깥(입출력·저장·플레이어 수)의 경계를 인터페이스로 고정
- `PlayerId`/`GameSession` 분리로 다인원 확장 여지 확보
- `ScorePolicy`/`SpeedPolicy`/`PieceGenerator`를 전략 패턴으로 분리해 규칙 변경에 대응
- `ScoreRepository`/`SettingsRepository`/`Renderer`를 포트로 분리해 저장 방식·렌더링 방식 교체에 대응

### 트레이드오프
- 팀 전체가 포트/어댑터, 전략 패턴 개념에 익숙해지는 학습 비용 발생 — 다만 이 자체가 수업이 평가하려는 역량으로 판단하여 감수하기로 함

### 후속 검토
- 2차 요구사항(아이템 모드) 기준으로 이 결정을 다시 점검한 결과는 [2차 요구사항 분석](requirements2-analysis.md) 참고


## 팀 역할 분담

| 담당 | 디렉토리 | 역할 |
|------|----------|------|
| 팀원1 | `ui/`, `test/performance/` | 사용자 입력, 화면, 콘솔 출력 |
| 팀원2 | `core/`, `test/core/` | 블록 생성·이동·회전, 셀 정보, 점수/속도 정책 |
| 팀원3 | `application/`, `storage/`, `bootstrap/`, `test/application/`, `test/storage/` | 게임 세션 진행, 점수·설정 저장, 전체 조립 |

### 남은 논의
"블록 N개/줄 M개마다 속도 몇 % 증가"의 구체적 수치는 점수 공식과 묶어서 팀 합의 안건으로 처리.

## 규정 확인 사항
