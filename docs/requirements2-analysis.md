# 2차 요구사항 분석

2차 요구사항(난이도, 확률 기반 블록 생성, 아이템 모드)을 1차(v1.0.0)에서 채택한 헥사고날 구조(`core` / `application` / `storage` / `bootstrap` / `ui`)에 비추어 분석한 기록. 요구사항별 변경 위치와 난이도, 현재 구조로 받아들이기 어려운 부분과 리팩터링 방향을 정리함. 채택 당시의 결정은 [아키텍처 결정 기록](architecture-decision.md) 참고.

## 결론

- **규칙을 바꾸는 요구는 잘 받아들임.** 난이도별 블록 확률·속도, 메뉴 추가, 저장 형식 확장은 정책 인터페이스와 층 분리 덕분에 구현체 추가 수준으로 끝남.
- **새로운 종류의 것을 추가하는 요구는 받아들이지 못함.** 아이템 모드는 `core`의 블록·칸 모델이 7가지 테트로미노에 고정돼 있어 모델 리팩터링이 먼저 필요함.
- 문제의 원인은 층 구조(헥사고날이냐 MVC냐)가 아니라 **도메인 모델 설계**임. 층 분리 덕분에 고칠 곳이 거의 `core` 하나로 모임.

## 1. 현재 구조와 MVC의 대응

현재 구조는 MVC를 버린 것이 아니라, MVC에 의존 방향 규칙을 더한 형태임.

| MVC        | 현재 구조                                              |
| ---------- | ------------------------------------------------------ |
| Model      | `core`(게임 규칙) + `application`(점수·속도·세션)      |
| View       | `ui/render` (`TextRenderer`, `TextFramePanel`)         |
| Controller | `ui/input` + `ui/screen` + `ScreenRouter`              |
| (추가)     | `storage`: 저장을 Model에서 분리한 포트 구현           |
| (추가)     | `bootstrap`: 조립을 한 곳에 모은 컴포지션 루트         |

## 2. 2차 요구사항별 적합도

| 2차 요구                                   | 변경 위치                                                        | 평가 |
| ------------------------------------------ | ---------------------------------------------------------------- | ---- |
| 난이도별 I블록 ±20% (룰렛 휠 선택)         | `PieceGenerator` 구현체 추가, `AppComposition`에서 주입          | 쉬움 |
| 1,000회 이상·±5% 확률 분포 테스트          | 생성기가 시드를 받는 순수 클래스라 바로 테스트 가능              | 쉬움 |
| 난이도별 속도 증가율 ±20%                  | `SpeedRule` 구현에 배율 추가                                     | 쉬움 |
| 시작 메뉴에 아이템 모드 추가               | `ScreenRouter.menuItems()`에 항목 추가                           | 쉬움 |
| 아이템으로 지운 줄도 기존 방식으로 점수    | `ScorePolicy`가 이미 지운 줄 수만 사용                           | 쉬움 |
| 난이도 설정 저장                           | `Settings`, 설정 파일 `schemaVersion` 1→2                        | 보통 |
| 스코어보드를 모드·난이도로 구분            | `GameResult`·`ScoreEntry` 필드 추가, 점수 파일 버전 1→2          | 보통 |
| 새 게임에 모드·난이도 전달                 | `ApplicationContext.newGame()` 매개변수 추가                     | 보통 |
| 줄 삭제 애니메이션                         | 지운 줄의 내용을 core가 보고하고, 세션이 연출 시간 동안 대기     | 어려움 |
| 줄 삭제 아이템 `L`, 무게추, 팀 아이템 3개  | 블록·칸 모델, 엔진 동작, 결과 형식 변경                          | 어려움 |
| 10줄마다 아이템 등장(미리보기에 바로 표시) | 지운 줄 수를 생성기에 전달하는 연결 필요                         | 보통 |

## 3. 잘 맞은 부분

- **정책 인터페이스**: `PieceGenerator`, `ScoreRule`, `SpeedRule`로 규칙이 분리돼 있어 난이도 요구 대부분이 구현체 교체로 해결됨. 1차에서 모호했던 "동일 확률" 문제도 7-bag 대신 가중치 생성기를 쓰면서 함께 해소됨(normal은 가중치 동일).
- **컴포지션 루트**: 조립이 `bootstrap`에만 있어, 모드에 따라 다른 규칙 묶음으로 게임을 만드는 지점이 이미 정해져 있음.
- **저장 형식 버전**: 설정·점수 파일 모두 버전 필드가 있어 기존 파일을 변환하며 필드를 추가할 수 있음.
- **Swing과 분리된 화면**: 메뉴·설정·스코어보드 변경을 창 없이 테스트할 수 있음.

## 4. 맞지 않는 부분

- **블록 = 7가지 enum**: `ActivePiece`, `Board.canPlace/place`, `RotationSystem`이 모두 `TetrominoType`을 전제로 함. 무게추(너비 4)나 블록 전체가 아이템인 경우를 표현할 수 없음.
- **칸이 블록 종류만 기억**: `Cell(kind, occupiedBy)`에 아이템을 둘 자리가 없음. `L`처럼 블록의 한 칸에 붙는 아이템을 담지 못함.
- **블록별 동작을 넣을 곳이 없음**: 아이템마다 다른 효과를 `PlayerEngine` 안의 분기로 넣어야 함. 아이템이 늘수록 엔진이 비대해짐.
- **삭제 규칙 고정**: `Board.clearFullLines()`는 꽉 찬 줄만 지움. `L`이 있는 줄처럼 다른 이유로 지우는 경로가 없음.
- **닫힌 결과 형식**: `EngineStep`의 필드가 하강·고정·삭제 3개로 고정돼, 새 사건(아이템 발동 등)마다 형식을 고쳐야 함.
- **삭제가 한 번에 끝남**: 고정 시점에 줄 삭제와 압축이 같이 끝나고 `ClearedRow`에는 행 번호만 남아, 애니메이션에 필요한 지운 줄의 내용이 없음.
- **ui가 core 값 타입을 직접 읽음**: `TextRenderer`·`BlockGlyphs`가 `Cell`·`TetrominoType`을 직접 사용해, core 모델을 바꾸면 영향이 UI까지 번짐.

## 5. MVC였다면

- 포트·조율자·저장 보장 같은 장치가 없어 1차 구현은 더 빨랐을 것.
- 흔한 Swing식 MVC는 Controller가 타이머와 게임 진행을, Model이 파일 저장까지 맡는 경우가 많음. 그러면 2차의 확률 분포 테스트나 저장 형식 변경은 오히려 불리했을 것.
- 아이템 모드는 MVC여도 똑같이 막힘. Model 안의 블록이 고정된 enum이었다면 같은 리팩터링이 필요함.
- 참조 코드는 `Block`을 부모로 두고 블록마다 하위 클래스(`IBlock` 등)를 두는 구조라, 무게추 같은 새 블록을 클래스 추가로 넣기가 비교적 자연스러움. 우리는 enum과 회전 좌표표로 더 간결하게 만든 대신 새로운 종류의 블록을 넣을 여지를 잃음. 이 차이는 MVC냐 헥사고날이냐가 아니라 모델 설계에서 나옴.

## 6. 더 좋았을 설계 (2차 리팩터링 방향)

층 구조는 유지하고 `core` 내부를 확장에 열린 형태로 바꿈.

- **블록 = 모양 데이터**: `Piece`를 칸 목록과 칸별 속성(블록 종류, 아이템)으로 표현. 7가지 테트로미노와 무게추 모양이 모두 같은 형식이 됨.
- **아이템 = 전략 객체**: `Item` 인터페이스에 고정 시 효과를 정의. 아이템 추가는 클래스 하나와 화면 문자 등록으로 끝남.
- **모드 = 규칙 묶음**: 블록 생성, 삭제 규칙, 아이템 효과를 모드별로 묶어 `bootstrap`에서 선택해 조립.
- **결과 = 이벤트 목록**: `EngineStep`을 하강·고정·줄 삭제(지운 칸 내용 포함)·아이템 발동 등의 이벤트 목록으로 바꿔, 새 사건이 생겨도 기존 코드가 깨지지 않게 함. UI는 줄 삭제 이벤트로 애니메이션을 그림.
- **생성기 장식**: 가중치 생성기를 10줄마다 아이템을 내는 생성기로 감싸 일반 모드와 아이템 모드가 같은 기반을 공유.
- **화면용 값으로 변환**: UI가 core 타입 대신 application이 넘겨주는 표시용 값(칸의 색 종류, 문자, 아이템 여부)을 읽게 해 core 변경이 UI로 번지지 않게 함.

### 반영 현황 (`refactor/core-model`, 카드 1)

- **반영함**
  - `Shape`(블록 모양) 도입, `TetrominoType`이 구현. 회전해도 같은 인덱스가 같은 칸을 가리키도록 회전 표 순서를 생성 시 정렬·검증
  - `Piece`(모양 + 칸별 아이템), `Cell`(모양 + 아이템), `CellKind` 제거
  - `Item`/`ItemContext`: 고정 시 효과. 처리 순서는 보드 기록 → 아이템 효과 → 꽉 찬 줄과 아이템 지정 줄 일괄 삭제
  - `PieceSource`/`PlainPieceSource`: 아이템 공급과 지운 줄 수 알림 (생성기 장식의 기반)
  - `ClearedRow`에 지운 칸 내용, `EngineStep`에 아이템 발동 목록 추가
- **다르게 한 것**: 결과를 완전한 이벤트 목록으로 바꾸지 않고 기존 drop/lock/clear 필드를 유지한 채 아이템 발동 목록만 추가함. application 작업이 동시에 진행 중이라 세션 코드가 바뀌지 않게 하기 위함
- **남은 것**
  - 무게추처럼 블록 단위로 이동 규칙이 바뀌는 동작(접촉 후 좌우 이동 금지, 낙하하며 삭제)의 확장 지점: 실제 무게추 카드에서 요구에 맞춰 추가
  - UI가 core 타입을 직접 읽는 구조는 그대로 둠

## 7. 교훈

> 확장성은 아키텍처 스타일보다 도메인 모델이 결정한다. 층은 변경이 퍼지는 범위를 줄여 주지만, 무엇이 바뀔 수 있는지는 모델이 정한다.

1차 요구사항만 보고 아이템까지 미리 일반화했다면 쓰이지 않을 추상화를 만든 셈이었을 것. 다만 "블록 종류가 늘어날 수 있다"는 정도의 변화는 enum 대신 데이터로 표현하는 것만으로 비용 없이 열어 둘 수 있었음.

## 8. 진행 순서

1. `refactor/core-model`: `Piece`, 아이템을 담는 `Cell`, `Item` 인터페이스, 이벤트형 결과로 core 모델 변경 (아이템 구현 전에 선행)
2. `feat/difficulty`: 가중치 생성기와 확률 테스트, 난이도별 속도, 설정·점수 파일 버전 변경, 모드·난이도별 스코어보드
3. `feat/item-mode`: 필수 아이템 2개와 팀 아이템 3개, 10줄 규칙, 메뉴, 줄 삭제 애니메이션
4. 팀 아이템 명세서(모양·기능) 작성: 평가 시 제공 필요
