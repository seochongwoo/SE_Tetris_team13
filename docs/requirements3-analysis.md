# 3차 요구사항 분석

3차 요구사항(`TeamProject_Req3.pdf`, 14쪽: 로컬 대전 모드, P2P 대전 모드, 최종 평가 기준 변경)을 v2.0.0의 헥사고날 구조(`core` / `application` / `storage` / `bootstrap` / `ui`)에 비추어 분석한 기록. 요구사항 목록, 파생 요구사항과 설계·환경 고려사항, 변경 위치와 난이도, 팀이 정해야 할 안건을 정리함. 작업 카드는 [3차 백로그](requirements3-backlog.md)에 있음.

## 결론

- **대전 규칙의 재사용 기반은 충분함.** `PlayerEngine`과 `SinglePlayerSession`이 인스턴스 단위이므로 두 플레이어의 진행에 재사용할 수 있음. 다만 공격 전달, 양쪽 일시정지, 경기 종료와 제한시간을 조정하는 대전 세션이 필요함. 공격 줄 모양에 필요한 정보(지운 줄의 칸 내용, 마지막 블록 위치)도 `EngineStep`이 이미 보고함.
- **core에 새로 필요한 것은 두 가지.** 보드 아래에서 줄을 밀어 넣는 기능과, 블록 고정 후 다음 블록 생성 전에 대기 줄을 반영하는 지점. 지금은 고정과 생성이 `lockActivePieceAndSpawnNext` 한 메서드에서 끝남.
- **P2P는 새 어댑터로 붙임.** 통신을 application의 포트로 정의하고 소켓 구현은 `storage`처럼 바깥 패키지(`network`)에 둠. 그러면 로비·동기화 규칙을 소켓 없이 테스트할 수 있음.
- **주요 위험은 상태 일치·종료 판정·실제 LAN 성능과 접속 환경.** P2P 양쪽의 경기 상태와 결과를 일치시키고 입력부터 화면 표시까지의 지연을 검증해야 함. Windows 방화벽, 여러 어댑터의 IP 표시, 평가장 네트워크 지연(p14)도 실제 PC 두 대로 리허설이 필요함.
- **최종 평가 기준이 강화됨(p13).** 비기능 요구사항, 코드 리뷰·리팩토링·버전관리 기록, 팀 아이템 명세서의 작성 품질을 평가함.

## 3. 현재 구조와의 적합도

| 요구                                          | 변경 위치                                                                                                              | 평가                   |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| 시작 메뉴에 대전·P2P 항목                     | `ScreenRouter.menuItems()`에 항목 추가                                                                                 | 쉬움                   |
| 플레이어 2명                                  | `PlayerEngine`·`SinglePlayerSession`을 두 개 만들고 묶는 대전 세션 추가                                                | 보통                   |
| 공격 줄 모양 (마지막 블록 칸 제외)            | `EngineStep`의 `ClearedRow`(지운 줄 칸 내용)와 `LockResult`(블록 모양·위치)로 계산                                     | 쉬움                   |
| 대기 줄 10줄 규칙                             | application의 순수 클래스(대기열)                                                                                      | 쉬움                   |
| 보드 아래에 줄 추가                           | `Board`에 새 메서드. 위로 밀려 넘치는 경우 판정                                                                        | 보통                   |

| 랙 표시, 끊김 처리                            | 주기적 확인 메시지(ping)와 시간 기준                                                                                   | 보통                   |
| 지연 200ms 이하                               | 전송량·처리 대기·렌더링을 함께 관리하고 실제 LAN에서 입력→화면 지연 측정                                               | 보통                   |
| 접속 자동화 테스트                            | localhost에서 서버·클라이언트를 띄우는 테스트, 가짜 통신으로 지연·끊김 재현                                            | 보통                   |

### 잘 맞는 부분

- **엔진이 인스턴스 단위**: 전역 상태가 없어 엔진 두 개가 서로 간섭하지 않음.
- **결과를 사실로 보고**: `EngineStep`이 지운 줄의 칸 내용과 고정된 블록 위치를 이미 담고 있어, 일반 줄 삭제의 공격 모양 계산에 기존 정보를 재사용할 수 있음. 아이템에 따른 빈칸·속성 처리는 별도 규칙과 검증이 필요함.
- **포트와 어댑터**: 저장소를 포트로 분리한 방식 그대로 통신 포트를 만들면, 대전 규칙은 소켓 없이 테스트할 수 있음.
- **시간을 숫자로 받는 세션**: 시간제한과 랙 판정을 가짜 시계로 정확히 테스트할 수 있음.
- **Swing을 모르는 화면**: 로비·대전 화면도 키 이름 문자열과 글자 격자로 테스트 가능.

### 맞지 않는 부분

- **고정과 생성이 붙어 있음**: 대기 줄을 "다음 블록이 생성되기 전"에 넣으려면 엔진이 고정 후 외부 입력을 받을 지점이 필요함. 공급자(`PieceSource`)처럼 엔진에 "고정 후 보드에 반영할 줄"을 넘겨주는 인터페이스를 두는 방향이 자연스러움.
- **보드에 아래에서 줄을 넣는 기능이 없음**: 지금 `Board`는 줄을 지우고 위 줄을 내리는 방향만 있음.
- **화면 크기가 고정**: `TextFrame.COLUMNS = 44`를 여러 화면이 직접 사용함. 대전 화면은 다른 크기의 격자를 쓰고, `TextFramePanel`이 격자 크기에 맞춰 창을 다시 맞춰야 함.
- **직렬화에 맞지 않는 모델**: 무게추·폭탄 모양(`WeightBlock.SHAPE`, `SoloBlock.SHAPE`)이 익명 클래스이고 아이템 클래스도 `Serializable`이 아님. p11 Tip처럼 객체를 그대로 직렬화하기보다, 통신용 데이터 형식(보드 칸 코드, 점수 등)을 따로 정하는 편이 안전함.
- **종료 확정과 연출이 연결됨**: `SinglePlayerSession`은 삭제 연출이 끝날 때까지 종료 처리를 미룰 수 있음. 대전은 논리적 패배 확정과 결과 표시를 분리해, 연출 중 상대의 추가 점수·공격이 결과를 바꾸지 않도록 해야 함.
- **단일 실행 흐름을 전제함**: `SinglePlayerSession`은 하나의 실행 흐름에서 호출해야 함. 수신 스레드가 세션을 직접 변경하지 않도록 메시지를 게임 실행 흐름에 전달하는 계약이 필요함.
- **설정이 1인 기준**: `Settings.keyBindings`가 플레이어 한 명분만 있음.

## 4. 구조 변경 방향

```
ui        : 대전 메뉴·모드 선택·대전 화면(보드 2개 + 대기 줄 + 타이머)·P2P 로비·랙 표시
application
  versus  : VersusSession (세션 2개, 공격 전달, 승패, 일시정지, 시간제한)
            AttackQueue   (대기 줄 최대 10, 아래 추가, 넘치면 아래 잘라냄, 꽉 차면 무시)
  port    : MatchTransport (연결, 메시지 송수신, 연결 상태), RecentHostRepository
core      : Board 아래에서 줄 추가 / 고정 후 대기 줄 반영 지점 / 공격 줄 모양 계산 / 공격 칸 Shape
network   : 소켓 기반 MatchTransport 구현 (서버·클라이언트, 메시지 형식, ping)
storage   : 최근 IP 저장소
bootstrap : 대전·P2P 조립
```

- 공격 흐름: 플레이어 A의 `EngineStep`(2줄 이상 삭제) → 공격 줄 계산 → B의 대기열 → B의 현재 블록 고정 → 아이템 효과·줄 삭제 → 대기 줄을 보드 아래에 추가 → 넘침 판정 → 다음 블록 생성. 넘침 또는 생성 실패 시 패배를 판정하며, 아이템 세부 순서는 안건 ⑭·⑮로 확정함.
- P2P 동기화는 두 방식 중 하나를 안건으로 정함.
  - **입력 전송**: 같은 초기 상태·난수 정책·입력 순서·진행 시간으로 양쪽이 같은 계산을 함. 같은 시드만으로는 일치를 보장하지 않음. 전송량이 작지만 양쪽 계산이 어긋나지 않게 보장해야 함.
  - **상태 전송**: 각자 자기 보드를 계산하고 바뀐 화면 정보만 보냄. 단순하고 p11 Tip에 가까움. 공격 줄은 이벤트로 따로 보냄.

### P2P 상태 관리 계약

카드 14에서 정책을 결정하고 카드 22에서 메시지 형식으로 구체화함. 다음 표의 권장안은 아직 팀 결정이 아니며, 선택한 동기화 방식에 맞춰 확정해야 함.

| 결정 대상           | 필요한 계약 / 권장안                                                                                                                |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 경기 상태           | 접속 중 → 연결 후 대기 → 경기 중 → 결과 표시 → 연결 후 대기. 연결 실패·끊김은 오류 표시 후 P2P 첫 화면으로 전환                     |
| 준비와 모드         | 양쪽이 같은 모드·설정에 준비해야 시작. 서버가 모드·시간을 바꾸면 양쪽 준비를 해제하는 안 제안                                       |
| 결과 확정           | 승패 확정 주체, 동시 패배 판정 단위, 공격·패배·시간 만료의 처리 순서 정의. 서버가 최종 결과를 확정·전달하는 안 제안                 |
| 시간과 일시정지     | 기준 시계, 시작 시점, 정지·재개, 종료 이후 입력 처리 정의. 서버의 단조 시계로 경과시간을 관리하고 정지 중 제한시간도 멈추는 안 제안 |
| 메시지 구분         | 경기 식별자와 필요한 순서 정보를 정의. 이전 경기 메시지를 새 경기에서 적용하지 않으며 공격 이벤트가 중복 반영되지 않게 함           |
| 상태 변경 실행 흐름 | 소켓 수신 결과는 큐 등으로 게임 실행 흐름에 전달. 게임 상태는 한 실행 흐름에서 변경하고 UI 반영 경로도 명시                         |

| 재대전과 자원 정리  | 재대전 시 보드·점수·공격 대기열·타이머·아이템 효과·준비 상태를 초기화. 끊김·나가기 시 소켓·수신 작업을 정리하고 재접속 가능하게 함  |

## 7. 최종 평가 대비 (p13)

- **팀 아이템 요구사항 명세서**: [아이템 명세서](item-specification.md)를 요구사항 명세 형식(ID, 설명, 우선순위, 수용 기준, 추적)으로 다시 정리함. 백로그 카드로 둠.
- **코드 리뷰 기록**: 3차의 모든 PR에 상대방 GitHub Review(Approve / Request changes)를 남김. 리뷰에서 나온 버그는 `bug` 이슈로 등록.
- **리팩토링 기록**: 4장의 core 리팩터링을 별도 카드와 PR로 진행해, 리팩토링 이력이 PR 단위로 보이게 함.
- **재점검**: 3차 개발이 끝나면 [요구사항 추적표](requirements-traceability.md)에 3차 항목을 추가하고 1·2차 항목을 다시 확인함.

### 성능 및 네트워크 검증

- **N3-01 측정 대상**: 키 입력부터 해당 변화가 화면에 표시될 때까지의 지연. ping RTT는 랙 감지용 보조 지표이며, localhost 테스트와 별도로 같은 LAN의 실제 PC 두 대에서 양방향 조작을 측정함. 로컬 화면과 상대 화면의 반응을 각각 기록함.
- **측정 절차**: 카드 14에서 입력 시작점·화면 표시 완료점, 조작 종류, 반복 횟수, 측정 방법·오차를 정함. 입력과 두 화면을 함께 촬영하거나 시계 오차를 통제한 계측을 사용함. 동기화되지 않은 두 PC의 타임스탬프를 단순히 빼서 지연으로 사용하지 않음.
- **판정·증거**: 빌드 버전, PC 사양, 네트워크 환경, 모드, 방향, 표본 수, 최대 지연, 200ms 초과 횟수와 측정 오차를 기록함. 평균만으로 통과시키지 않으며, 측정 오차를 고려해 200ms 이하인지 확인할 수 없는 경우 재측정함. 초과 사례는 원인 분석·개선 후 다시 검증함. 측정 결과는 해당 환경·표본의 검증 증거로 남김.
- **느린 네트워크**: 지연·끊김 자동화 테스트와 실제 환경 리허설로 랙 표시·회복·오류·첫 화면 복귀·재접속을 확인함. 정상 LAN 성능 결과와 저하 환경의 예외 처리 결과를 구분해 기록함.
- **완료 증거 연결**: 카드 24는 세 모드 통합·재대전 자동화 결과와 실제 LAN 성능 측정으로 완료 판정. 카드 26은 CI 자동화 검증, 카드 28은 배포 빌드의 리허설·성능 재확인과 커버리지 보고서를 요구사항 추적표에 연결함.
