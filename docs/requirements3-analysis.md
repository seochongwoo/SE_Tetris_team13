# 3차 요구사항 분석

3차 요구사항(`TeamProject_Req3.pdf`, 14쪽: 로컬 대전 모드, P2P 대전 모드, 최종 평가 기준 변경)을 v2.0.0의 헥사고날 구조(`core` / `application` / `storage` / `bootstrap` / `ui`)에 비추어 분석한 기록. 요구사항 목록, 숨은 요구사항, 변경 위치와 난이도, 팀이 정해야 할 안건을 정리함. 작업 카드는 [3차 백로그](requirements3-backlog.md)에 있음.

## 결론

- **대전 규칙은 지금 구조로 잘 받아들임.** `PlayerEngine`과 `SinglePlayerSession`이 인스턴스 단위라 플레이어 둘은 두 개를 만들면 됨. 공격 줄 모양에 필요한 정보(지운 줄의 칸 내용, 마지막 블록 위치)도 `EngineStep`이 이미 보고함.
- **core에 새로 필요한 것은 두 가지.** 보드 아래에서 줄을 밀어 넣는 기능과, 블록 고정 후 다음 블록 생성 전에 대기 줄을 반영하는 지점. 지금은 고정과 생성이 `lockActivePieceAndSpawnNext` 한 메서드에서 끝남.
- **P2P는 새 어댑터로 붙임.** 통신을 application의 포트로 정의하고 소켓 구현은 `storage`처럼 바깥 패키지(`network`)에 둠. 그러면 로비·동기화 규칙을 소켓 없이 테스트할 수 있음.
- **가장 큰 위험은 구현보다 환경.** Windows 방화벽, 어댑터가 여러 개일 때의 IP 표시, 평가장 네트워크 지연(p14)은 코드만으로 해결되지 않으므로 리허설이 필요함.
- **최종 평가 기준이 강화됨(p13).** 비기능 요구사항, 코드 리뷰·리팩토링·버전관리 기록, 팀 아이템 명세서의 작성 품질을 평가함.

### 잘 맞는 부분

- **엔진이 인스턴스 단위**: 전역 상태가 없어 엔진 두 개가 서로 간섭하지 않음.
- **결과를 사실로 보고**: `EngineStep`이 지운 줄의 칸 내용과 고정된 블록 위치를 이미 담고 있어, 공격 줄 계산에 엔진을 고칠 필요가 없음.
- **포트와 어댑터**: 저장소를 포트로 분리한 방식 그대로 통신 포트를 만들면, 대전 규칙은 소켓 없이 테스트할 수 있음.
- **시간을 숫자로 받는 세션**: 시간제한과 랙 판정을 가짜 시계로 정확히 테스트할 수 있음.
- **Swing을 모르는 화면**: 로비·대전 화면도 키 이름 문자열과 글자 격자로 테스트 가능.

### 맞지 않는 부분

- **고정과 생성이 붙어 있음**: 대기 줄을 "다음 블록이 생성되기 전"에 넣으려면 엔진이 고정 후 외부 입력을 받을 지점이 필요함. 공급자(`PieceSource`)처럼 엔진에 "고정 후 보드에 반영할 줄"을 넘겨주는 인터페이스를 두는 방향이 자연스러움.
- **보드에 아래에서 줄을 넣는 기능이 없음**: 지금 `Board`는 줄을 지우고 위 줄을 내리는 방향만 있음.
- **화면 크기가 고정**: `TextFrame.COLUMNS = 44`를 여러 화면이 직접 사용함. 대전 화면은 다른 크기의 격자를 쓰고, `TextFramePanel`이 격자 크기에 맞춰 창을 다시 맞춰야 함.
- **직렬화에 맞지 않는 모델**: 무게추·폭탄 모양(`WeightBlock.SHAPE`, `SoloBlock.SHAPE`)이 익명 클래스이고 아이템 클래스도 `Serializable`이 아님. p11 Tip처럼 객체를 그대로 직렬화하기보다, 통신용 데이터 형식(보드 칸 코드, 점수 등)을 따로 정하는 편이 안전함.
- **설정이 1인 기준**: `Settings.keyBindings`가 플레이어 한 명분만 있음.

## 4. 구조 변경 방향

```
ui        : 대전 메뉴·모드 선택·대전 화면(보드 2개 + 대기 줄 + 타이머)·P2P 로비·랙 표시
application
  versus  : VersusSession (세션 2개, 공격 전달, 승패, 일시정지, 시간제한)
            AttackQueue   (대기 줄 최대 10, 아래 추가, 넘치면 아래 잘라냄, 꽉 차면 무시)
  port    : MatchTransport (연결, 메시지 송수신, 연결 상태), RecentHostRepository
core      : Board 아래에서 줄 추가 / 고정 후 대기 줄 반영 지점 / 공격 줄 모양 계산 / 공격 칸 Shape
network   : 소켓 기반 MatchTransport 구현 (서버·클라이언트, 메시지 형식, ping)
storage   : 최근 IP 저장소
bootstrap : 대전·P2P 조립
```

- 공격 흐름: 플레이어 A의 `EngineStep`(2줄 이상 삭제) → 공격 줄 계산 → B의 대기열 → B의 다음 블록 고정 직후 엔진이 대기열의 줄을 보드 아래에 추가 → 넘치면 B 종료.
- P2P 동기화는 두 방식 중 하나를 안건으로 정함.
  - **입력 전송**: 같은 시드와 같은 엔진으로 양쪽이 같은 계산을 함. 전송량이 작지만 양쪽 계산이 어긋나지 않게 보장해야 함.
  - **상태 전송**: 각자 자기 보드를 계산하고 바뀐 화면 정보만 보냄. 단순하고 p11 Tip에 가까움. 공격 줄은 이벤트로 따로 보냄.

## 5. 팀이 정할 안건

[미확정 사항](open-questions.md)의 안건 번호를 이어서 씀. 결정되면 그 문서의 표로 옮김.

| # | 안건 | 원문 | 제안 |
| --- | --- | --- | --- |
| ⑩ | 공격 줄이 들어와 블록이 보드 위로 밀려 넘칠 때 | p5 "더 이상 블럭을 쌓을 수 없게 되면 종료" | 밀려난 칸이 보드 밖으로 나가면 그 플레이어 패배 |
| ⑪ | 시간제한 모드의 시간 | p3 "타이머를 정해서" | 기본 2분, 시작 전 1·2·3분 중 선택 |
| ⑫ | 시간제한에서 점수가 같을 때 | 없음 | 무승부로 표시 |
| ⑬ | 두 명이 같은 순간 끝났을 때 | 없음 | 무승부로 표시 |
| ⑭ | `L`·폭탄·연쇄 삭제로 지운 줄도 공격인가 | p4 "2줄 이상 블럭을 삭제하면" | 줄 단위로 지운 것(꽉 찬 줄, `L`)만 공격. 칸 단위 삭제(폭탄, 연쇄)는 제외 |
| ⑮ | 공격 줄 모양에서 빼는 "마지막 블록" | p4 | 지운 줄에 걸친 마지막 블록의 칸만 비움. 무게추가 만든 줄은 무게추 칸을 비움 |
| ⑯ | 대전에도 난이도를 적용하는가 | 없음 | 설정의 난이도를 두 명에게 똑같이 적용 |
| ⑰ | 양쪽 블록 순서 | 없음 | 같은 시드로 두 명에게 같은 순서 (공정성) |
| ⑱ | 대전 중 일시정지 | 1차 p8 | 로컬은 둘 다 정지. P2P는 한쪽이 멈추면 양쪽 정지 |
| ⑲ | 1P·2P 기본 키 | 없음 | 1P는 키보드 왼쪽 묶음(WASD 등), 2P는 방향키 묶음. 일시정지·게임 메뉴 키는 공통 |
| ⑳ | P2P 동기화 방식 | p11 Tip | 4장의 두 방식 중 선택 |
| ㉑ | 랙·끊김 기준 | p10 "직접 정의하여 관리" | 왕복 지연 200ms 초과 시 랙 표시, 3초 무응답 시 끊김 처리 (평가장 환경으로 조정) |
| ㉒ | 포트 번호와 저장할 최근 IP 개수 | 없음 | 고정 포트 하나, 최근 IP 5개 |

## 6. 위험 요소와 대비

| 위험 | 대비 |
| --- | --- |
| Windows 방화벽이 서버 소켓 차단 | 처음 실행 때 허용 안내를 화면에 표시. 시연 노트북 두 대에서 미리 허용. 평가 가이드에 절차 추가 |

| 평가장 Wi-Fi가 느리거나 기기끼리 막힘 | 랙 표시가 동작하는지 테스트로 확인. 휴대폰 핫스팟 등 예비 네트워크 준비 |
| 양쪽 빌드가 다름 | 접속 직후 버전을 교환하고, 다르면 오류 메시지 |

| 커버리지 하락 (소켓 코드는 테스트가 어려움) | 통신을 포트로 분리해 규칙은 가짜 통신으로 테스트, 소켓 어댑터는 localhost 테스트 |

## 7. 최종 평가 대비 (p13)

- **팀 아이템 요구사항 명세서**: [아이템 명세서](item-specification.md)를 요구사항 명세 형식(ID, 설명, 우선순위, 수용 기준, 추적)으로 다시 정리함. 백로그 카드로 둠.
- **코드 리뷰 기록**: 3차의 모든 PR에 상대방 GitHub Review(Approve / Request changes)를 남김. 리뷰에서 나온 버그는 `bug` 이슈로 등록.
- **리팩토링 기록**: 4장의 core 리팩터링을 별도 카드와 PR로 진행해, 리팩토링 이력이 PR 단위로 보이게 함.
- **재점검**: 3차 개발이 끝나면 [요구사항 추적표](requirements-traceability.md)에 3차 항목을 추가하고 1·2차 항목을 다시 확인함.
