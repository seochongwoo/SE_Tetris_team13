# 2차 요구사항 작업 진행 제안

2차 요구사항(난이도, 확률 기반 블록 생성, 아이템 모드)을 두 명이 어떻게 나눠 진행할지에 대한 제안입니다.

- A: 1차에서 `core`, `ui` 담당
- B: 1차에서 `application`, `storage`, `bootstrap` 담당

## 1. 진행 방식

- **기능 단위로 나눕니다.** core / ui / application 같은 층이 아니라, 사용자가 보는 기능 하나를 카드 하나로 만듭니다. 카드 하나가 core부터 화면까지 걸치므로, 각자 자기가 맡지 않았던 영역도 자연스럽게 익히게 됩니다.
- **배정하지 않고 가져갑니다.** 백로그 위쪽에서 선행 카드가 끝난 카드를 각자 하나씩 가져갑니다. 작업량을 미리 똑같이 나누지 않습니다.
- **기록은 작업하면서 쌓습니다.** 카드는 Trello에, 문제와 해결 과정은 GitHub Issue와 PR에 남깁니다. 2차 요구사항의 프로젝트 관리 항목(할 일 배정, 진척 상황, 이슈 추적, 브랜치·PR 정책)을 따로 문서화하지 않아도 이 기록이 근거가 됩니다.

- 1번이 아이템 관련 카드 전부의 선행 작업인 이유는 [2차 요구사항 분석](requirements2-analysis.md)에 정리했습니다. 요약하면 현재 core가 7가지 테트로미노 기준으로 고정돼 있어, 아이템을 넣기 전에 블록·칸 구조부터 바꿔야 합니다.
- 5번에서 기록에 모드(일반/아이템)도 함께 저장해 두면, 6번 이후 스코어보드를 다시 고치지 않아도 됩니다.
- 카드별 담당·완료일·PR은 [백로그 진행 현황](requirements2-backlog.md)에 기록합니다.

## 3. 진행 순서

### 1단계: 기반 다지기
- 0번은 첫날 같이 끝냅니다.
- 1번은 core 구조를 가장 잘 아는 A가 먼저 진행합니다. 시작 전에 새 타입 설계를 둘이서 짧게 맞추고, PR은 B가 리뷰합니다.
- 그동안 B는 1번과 겹치지 않는 2 → 4 → 5를 진행합니다. 이 카드들은 ui까지 걸쳐 있어 ui 구조를 익히는 기회도 됩니다.

### 2단계: 아이템 모드 뼈대
- 6, 7, 3, 12를 그때 비어 있는 사람이 가져갑니다.
- 1번을 리뷰한 B가 7번(`L`)을 맡으면 core 경험이 생깁니다.

### 3단계: 아이템 확장과 마무리
- 8번과 팀 아이템 9~11번을 한 장씩 나눠 가져갑니다.
- 아이템 명세서(형태·기능)를 작성합니다. 평가 시 평가하는 팀에 제공해야 합니다. 초안은 [아이템 모드 명세](item-spec.md)에 있습니다.
- 13번 릴리즈로 마무리합니다.

## 4. 운영 규칙

- **진행 중인 카드는 한 사람당 1장**: 끝내고 다음 카드를 가져갑니다. 맡을 카드를 미리 쌓아 두지 않습니다.
- **완료 기준**: 테스트 추가, 상대방 PR 리뷰, 이슈를 닫는 PR(`Closes #번호`), 필요한 문서 갱신.
- **충돌 관리**: 1번이 진행되는 동안 core를 크게 건드리는 카드는 시작하지 않습니다. 3번 생성기는 1번에서 `PieceGenerator` 인터페이스가 어떻게 바뀌는지 정해진 뒤 시작합니다.
- **짧은 공유**: 하루나 이틀에 한 번 채팅으로 "한 것 / 할 것 / 막힌 것"을 세 줄씩 공유합니다.
- **커버리지**: 중간평가 기준 Line Coverage 50% 이상을 PR마다 유지합니다.

- [ ] 팀 아이템 3개의 아이디어

## 6. B 담당 구현 브랜치와 검증

카드별 브랜치를 사용합니다. 선행 PR이 아직 머지되지 않았다면 앞 브랜치에서 다음 브랜치를 만들고, PR의 base도 앞 브랜치로 지정합니다. 머지 후에는 다음 PR의 base를 main으로 바꿉니다. Squash 머지를 쓴 경우 이미 머지된 변경이 다시 보이지 않도록 후속 브랜치를 rebase합니다.

| 카드 | 브랜치 | 최초 PR base | 구현·로컬 검증 |
| --- | --- | --- | --- |
| 2 | `feat/difficulty-settings` | `main` | 설정 화면·v1→v2 호환 읽기·저장·초기화, 284개 테스트 통과·라인 91.3% |
| 4 | `feat/difficulty-speed` | `feat/difficulty-settings` | 레벨당 감소량 80/100/120ms, 시작 시 난이도 고정·실제 엔진 가속, 298개 테스트 통과·라인 91.4% |
| 5 | `feat/scoreboard-mode-difficulty` | `feat/difficulty-speed` | 조합별 상위 10개·화면 필터·v1→v2 호환 읽기·게임 결과 분류, 308개 테스트 통과·라인 91.6% |

브랜치 시작점 `ff7b68a`는 main에 계획 문서만 추가된 커밋입니다. 4·5번의 기능상 선행 카드는 2번이며, 위 브랜치 연결은 순차 구현과 리뷰를 위한 것입니다.
로컬 구현·검증과 카드 완료는 구분합니다. GitHub Issue 연결(`Closes #번호`), PR 생성, 상대방 리뷰 및 Trello 상태 갱신은 별도로 필요합니다.

### 구현 범위와 연결 지점

- 난이도 기본값은 NORMAL. 기존 설정·점수는 읽을 때 보존하고 저장할 때 버전 2로 전환합니다.
- 가속 기준은 레벨당 낙하 간격 감소량 EASY 80ms / NORMAL 100ms / HARD 120ms입니다. 초기 1초·최소 100ms·10줄마다 레벨 상승은 동일합니다. 추가 점수 배율은 적용하지 않습니다.
- 스코어보드는 일반/아이템 × EASY/NORMAL/HARD의 여섯 조합별로 상위 10개를 보관합니다. ←/→는 난이도, ↑/↓는 모드를 전환합니다.
- 3번은 `Settings.difficulty()`를 블록 생성기에 연결하면 됩니다. 현재 생성기는 기존 7-bag입니다.
- 6번은 아이템 엔진을 조립한 뒤 `SinglePlayerSession(engine, scoring, speed, GameMode.ITEM, difficulty)`로 생성하면 결과·저장·순위 화면에 분류가 전달됩니다. 아이템 메뉴·규칙 자체는 이번 범위에 포함하지 않습니다.
- core 소스는 변경하지 않았습니다. A의 리팩터링과 통합할 때 세션의 엔진 결과 해석 부분은 별도로 맞춰야 합니다.
